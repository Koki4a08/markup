# Supabase backend

One Supabase project serves the website (sign in and sign up), the editor (web + desktop) and the extension. Plan: [`docs/superpowers/plans/2026-11-24-accounts-and-cloud.md`](../docs/superpowers/plans/2026-11-24-accounts-and-cloud.md).

```
migrations/
  20261124120000_accounts.sql      profiles (created on signup), user_settings
  20261124120100_billing.sql       subscriptions, billing_events, user_quota()
  20261124120200_cloud_files.sql   cloud_files, share_links, "files" bucket + policies, my_storage()
  20261124120300_usage_daily.sql   personal usage stats
```

Every table has RLS with owner-scoped policies and explicit column grants; `anon` has no access to any table. `subscriptions` and `billing_events` are written only by the service role (payment webhook). Storage quota: 500 MiB free, 20 GiB with an active subscription.

## Apply

The project should be in an EU region (Frankfurt).

```sh
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
```

Change the schema only with a new migration file here, never in the dashboard.

## Dashboard settings

Authentication → URL Configuration

- Site URL: `https://markup.here`
- Redirect URLs: `https://markup.here/**`, `http://localhost:5173/**` (links carry `?next=` and `?mode=`)

Authentication → Sign In / Providers

- Email: on, "Confirm email" on, minimum password length 8.
- GitHub: create an OAuth app on GitHub with the callback `https://<project-ref>.supabase.co/auth/v1/callback`, then paste its client id and secret here. The secret stays in the dashboard only.

## Auth emails (Send Email Hook)

Supabase does not send auth emails. The Edge Function `send-email` receives every auth email through the Send Email Hook, renders Markup's templates (HTML + plain text, logo as an inline image) and sends them through the private Mail API.

```
functions/
  send-email/index.ts       Deno entry
  send-email/handler.ts     verifies the hook signature, builds and sends the emails
  _shared/mailer.ts         Mail API client: validation, timeout, retries (429/502/503 only), JSON logs
  _shared/webhook.ts        Standard Webhooks signature check
  _shared/email/            layout, templates, assets.ts with the logo and cursor (generated by scripts/gen-email-assets.mjs)
  _tests/                   Vitest, fetch mocked: pnpm vitest run --project supabase-functions
```

Handled types: signup, magic link, recovery, invite, email change (both emails when secure change is on), reauthentication code, and the security notices (password, email, phone, identity, MFA changed) when they are enabled.

Set it up once:

1. Secrets (server only, never in git or a `VITE_*` variable). Copy `functions/.env.example` to `functions/.env`, fill it in, then:
   ```sh
   npx supabase secrets set --env-file supabase/functions/.env
   ```
   `MAILER_URL`, `MAILER_API_KEY`, `SEND_EMAIL_HOOK_SECRET`, optional `MAIL_REPLY_TO` and `SITE_URL`. `SUPABASE_URL` is provided by Supabase.
2. Deploy (Supabase Auth signs the call itself, so no JWT check):
   ```sh
   npx supabase functions deploy send-email --no-verify-jwt
   ```
3. Authentication → Hooks → Send Email → HTTPS, URL `https://<project-ref>.supabase.co/functions/v1/send-email`. Generate the secret, put it in `SEND_EMAIL_HOOK_SECRET` (step 1 again), enable the hook. From now on Supabase stops sending its own emails.
   Never enable the hook before the function is deployed with its secrets: every auth email then fails with a server error.
4. Authentication → Rate Limits: keep emails at a modest rate (for example 30 per hour). The Mail API has its own limit; the function retries 429 briefly and then reports "Too many emails" to the user.
5. Email OTP expiration stays at 1 hour, the value the templates mention (`LINK_EXPIRY` in `_shared/email/templates.ts`).

The hook must answer within about 5 seconds, so the function caps each send at 3.5 s and all retries at 4.5 s. It never retries a timeout, because the Mail API may already have accepted the message. SPF, DKIM, DMARC and PTR are managed on the mail server, not here.

## Keys

| Key | Where it goes | Secret? |
|---|---|---|
| Project URL | `VITE_SUPABASE_URL` in the website (and later the app) | No |
| Publishable key (`sb_publishable_…`, or the legacy anon key) | `VITE_SUPABASE_PUBLISHABLE_KEY` | No: RLS protects the data |
| Secret key / service role | Edge Function secrets only | **Yes**: never in a repo, a `VITE_*` variable, the desktop binary or the extension |
| `MAILER_API_KEY`, `SEND_EMAIL_HOOK_SECRET` | Edge Function secrets only | **Yes**: same rules |
